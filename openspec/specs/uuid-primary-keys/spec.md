# uuid-primary-keys Specification

## Purpose

Establish UUID v7 primary keys across all domain models in the `school` app and the custom user model, so every entity is identified by a time-ordered UUID generated by Django at instance creation, with migrations regenerated from a clean slate for adoption.

## Requirements

### Requirement: UUID v7 primary keys on domain models
Every project model in the `school` app (`Student`, `Teacher`, `StudentGroup`, `Subject`, `Course`, `SchoolCycle`, `NonSchoolDay`, `AttendanceSession`, `AttendanceRecord`, `ClassSchedule`) SHALL have a UUID v7 primary key named `id`, generated by Django at instance creation via the `uuid6` package's `uuid7` callable, non-editable, and exposed to the ORM and Django forms as a `UUIDField`. Foreign-key columns referencing these models and the `StudentGroup`–`Student` many-to-many through table SHALL store UUID values accordingly.

#### Scenario: New model instance receives a UUID v7 id
- **WHEN** any `school` model instance is created without an explicit id and saved
- **THEN** its `id` is a UUID whose version is 7 and it is stored in a UUID-typed primary-key column

#### Scenario: Foreign keys follow the primary-key type
- **WHEN** migrations are generated for the models in this change
- **THEN** every `ForeignKey` and many-to-many column referencing a project model is a UUID column, with no remaining auto-increment integer columns on project tables

#### Scenario: Admin and panel handle UUID ids
- **WHEN** a staff user edits any project model in the admin or a teacher navigates the teacher panel
- **THEN** object URLs embed the UUID primary key and the corresponding pages load successfully

### Requirement: Custom user model with UUID v7 primary key
The system SHALL define a custom user model `accounts.User` extending `AbstractUser` with a UUID v7 primary key generated via `uuid6`'s `uuid7`, and `AUTH_USER_MODEL` SHALL reference it. Authentication flows (allauth login, Django admin, session auth for the attendance API) and the `Teacher.user` one-to-one link SHALL operate against the custom user model without behavior change.

#### Scenario: Users are stored with UUID primary keys
- **WHEN** a user account is created (superuser, imported teacher user, or via the admin)
- **THEN** the user row's primary key is a UUID v7 value in a UUID column

#### Scenario: Existing auth flows keep working
- **WHEN** a teacher logs in through allauth and an admin logs in through the Django admin
- **THEN** both authenticate successfully against `accounts.User` and reach their usual post-login destinations

#### Scenario: Teacher profile links to custom user
- **WHEN** a `Teacher` is linked to a user account
- **THEN** the one-to-one relation resolves to the `accounts.User` instance and teacher-scoped views and API auth behave as before

### Requirement: Clean migration reset for adoption
Adopting UUID primary keys SHALL be done by resetting the dev database and regenerating migrations: the previous `school` migrations `0001`–`0008` and the SQLite database SHALL be replaced by fresh initial migrations for `accounts` and `school`, and the dev data SHALL be restorable via the `seed_dev_data` command. No data-preserving migration from integer keys SHALL be required.

#### Scenario: Fresh install reproduces the full schema
- **WHEN** a developer deletes the SQLite database, runs `makemigrations`, migrates, and runs `seed_dev_data`
- **THEN** all tables exist with UUID primary keys and seeded dev data (superuser, teachers, students, groups, subjects, cycles, courses, schedules, attendance) is present

#### Scenario: Test suite passes on the new schema
- **WHEN** the full Django test suite runs against the regenerated migrations
- **THEN** all existing school, teachers, and api tests pass without data from the previous schema
